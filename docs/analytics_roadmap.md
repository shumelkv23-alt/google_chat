# Дорожная карта: аналитика трендов + кластеры + тесты

> Решения на входе: чат — **агрегатор многих компаний** (нужно поле `company`);
> формат — **пошаговый план под реализацию**. Документ ведём по мере выполнения.

## Диагноз

Таблица `vacancies` ([app/db/models.py](../app/db/models.py)) хранит
`title / salary / status / team / owner / location / description / additional_info`.
Для запрошенной аналитики не хватает **структурных осей**:

| Запрос пользователя | Нужная ось | Было |
|---|---|---|
| Востребованность технологий | `skills[]` (нормализованные) | только свободный текст |
| Восходящие / нисходящие тренды | `skills[]` + `created_at` по бакетам | частично |
| Кластер «спец × зп × компания» | `company`, `role_category`, `seniority` | нет |

Вывод: ~80% работы — извлечение и **нормализация** данных. Аналитика поверх — это
SQL с `GROUP BY` и `date_trunc`.

## На что обратить внимание (грабли)

1. **Нормализация — сердце.** Без канонизации `python==питон==py` тренды развалятся.
   Чистые функции → покрыты юнит-тестами.
2. **Deepseek игнорирует мягкие инструкции** — новые поля в промпт только директивно,
   с примерами; проверять eval-прогоном.
3. **Тренды требуют истории** — на 5 вакансиях «тренд» это шум. Порог `min_count`.
4. **Зарплата — медиана, не среднее** (`PERCENTILE_CONT`), выбросы перекосят avg.
5. **NULL не должен ронять аналитику** — `COALESCE(..., 'не указано')`.
6. **Идемпотентность ревизий** — новые поля в `_FIELD_MAP` / `_REVERTABLE_FIELDS`,
   сторожит `tests/unit/test_field_map_consistency.py`.

## Фаза 1 — модель данных (фундамент)

- `Vacancy`: `company TEXT?`, `seniority TEXT?`, `role_category TEXT?`,
  `skills TEXT[] NOT NULL DEFAULT '{}'`.
- Индексы: GIN на `skills` (фильтр `@>`), btree на `created_at` (оконная аналитика).
- Миграция `alembic/versions/0006_vacancy_enrichment.py` (по образцу 0005), бэкфилл не нужен.
- **Проверка:** `alembic upgrade head` / `downgrade -1` на `chatbot_test`; смоук зелёный.

## Фаза 2 — извлечение + нормализация (критический путь)

- `app/services/skill_normalizer.py`, `seniority_normalizer.py`, `role_normalizer.py`,
  `company_normalizer.py` — чистые модули (как `posting_heuristic`).
- Промпты `extractor.py` (`_SYSTEM_BASE`, `_SYSTEM_FULL`) и `batch_extractor.py`:
  директивно + few-shot для `skills`, `company`, `seniority`, `role_category`.
- Валидаторы `ExtractionResult` (`BatchItem` наследует → батч бесплатно).
- `_FIELD_MAP` + `_REVERTABLE_FIELDS` + конструктор `_create_vacancy`.
- **Проверка:** прогон экстрактора на реальных постах; `test_field_map_consistency` зелёный.

## Фаза 3 — тренды

`app/services/trends.py`:
- `top_skills(status, days, limit)` — востребованные / менее востребованные.
- `skill_trend(skill, bucket, windows)` — временной ряд спроса.
- `rising_falling(bucket, min_count)` — сравнение двух окон, growth%.
- Чистая `compute_trend_direction(prev, cur)` — юнит-тест без БД.

## Фаза 4 — кластеры (спец × зп × компания)

`app/services/clusters.py` (структурный подход, детерминированный):
- `salary_by_company(role_category?, seniority?)` — медиана/min/max/count по компаниям.
- `role_salary_matrix(days)` — `GROUP BY (role_category, seniority)` + медиана.
- `company_demand(limit)` — каких спецов / стек чаще ищет каждая компания.
- Фаза 4b (опц., потом): ML-кластеризация эмбеддингов — не лезть, пока структура не покрыта.

## Фаза 5 — интенты + графики

- `IntentKind += skill_demand | trends | salary_by_company | role_matrix`.
- few-shot в `intent_router._SYSTEM`; рендер в `charts.py`.

## Фаза 6 — тесты

- **Unit:** нормализаторы (параметризованно), `compute_trend_direction`, extractor новых полей,
  `field_map_consistency`, intent-классификация.
- **Integration** (`chatbot_test`): trends/clusters пайплайны, граничные (пусто/NULL/одна вакансия).
- **Eval** (`eval/`): golden-датасет → precision/recall по `skills` (F1 на множествах) / `company` / `seniority`.
- **RAG-качество:** golden Q→A, опора на БД; LLM-as-judge на Claude (отдельно).
- **Регрессии:** ivfflat probes, идемпотентность ревизий новых полей.

## Порядок

Фаза 0/измерение → 1 → 2 → (eval сразу) → 3 ∥ 4 → 5 → тесты 1/2/4/5.
Критический путь — Фаза 2: плохое извлечение обесценит всю аналитику.

### Приоритет 1 — ✅ СДЕЛАНО (2026-06-17)

Закрыто 18 интеграционных тестов (`test_interaction_analytics.py` +13,
`test_rag_context.py` +5, новый). Результат по целевым модулям:

| Модуль | Было | Стало |
|---|---|---|
| `interaction_handler.py` | 40% | **84%** |
| `rag.py` | 24% | **100%** |
| `analytics.py` | 22% | **86%** |

Попутно найден и пофикшен реальный баг в `rag.py`: `SET ivfflat.probes = 50` стоял
после запроса сообщений, поэтому поиск по сообщениям шёл с дефолтным `probes=1` и на
малых данных (чат 5-10 сообщений/день) молча возвращал пусто. `SET` перенесён выше
обоих запросов — теперь и сообщения, и вакансии обходят все кластеры. Тест стережёт.

**`interaction_handler.py` — 40% (240 строк, ~144 не покрыто)**

Самый большой разрыв в коде, который активно используется. Непокрытые пути:
- Ветки диспатча `count`, `list_recent`, `search`, `chart`, `add_vacancy`, `close_vacancy`
- Текстовые форматтеры для каждого интента
- Ответ «нет данных» для trends/clusters при пустых результатах

Стратегия: `monkeypatch` на `classify_intent` (как в `test_interaction_analytics.py`) +
seed одной вакансии + проверка подстроки в `payload["text"]`.
Оценка: ~6–8 тестов → +8–10 п.п. к общему покрытию.
→ **Готово: 84%.** +13 тестов (count/list_recent/chart/salary_chart + RAG-fallback с
обработкой ошибки + пустые ответы trends/salary_by_company/role_matrix). Остаток ~16% —
ветки сборки карточек QuickChart (нужна сеть, интеграция её не трогает) и плюрализаторы.

**`rag.py` — 24% (~60 строк не покрыто)**

RAG — ключевое качество бота, но почти без тестов. Непокрытые пути:
- `build_rag_context()` при пустой БД
- `build_rag_context()` при наличии вакансий (проверить что vacancy-текст попадает в контекст)
- Порядок приоритизации источников (вакансии vs сообщения)

Стратегия: integration-тест с seed-вакансией, мок эмбеддинга (возвращает нулевой вектор),
проверить что title вакансии есть в возвращаемой строке контекста.
Оценка: ~4 теста → +4–5 п.п.
→ **Готово: 100%.** +5 тестов (пустая БД, вакансия в контексте, сообщение в контексте,
память диалога, приоритет источников). Здесь же всплыл баг с ivfflat-probes (см. выше).

**`analytics.py` — 22% (старый сервис, ~80 строк не покрыто)**

Осторожно: этот модуль фактически вытеснён `trends.py` / `clusters.py`, но не удалён.
Перед написанием тестов — проверить через `grep -r "from app.services.analytics"`, используется
ли он ещё где-то. Если нет — удалить вместо покрытия (мёртвый код не стоит тестов).
→ **Готово: 86%.** Проверка grep'ом: модуль **живой** (импортит `interaction_handler` —
count/list_recent/group_count/list_vacancy_salaries), НЕ удаляем. Покрылся транзитивно
через тесты диспатча, отдельный файл не понадобился. Остаток — ветка topic-эмбеддинга.

### Приоритет 2 — качество и безопасность регрессий

**`edits.py` — 61% (~40 строк)**

Логика отмены изменений (`revert`) — чувствительная, при баге данные портятся молча.
Непокрыто: частичный revert (только некоторые поля), revert при отсутствии ревизии,
revert новых полей (`company`, `skills`, `seniority`, `role_category`).
Стратегия: unit-тест с фейковым vacancy-dict и вызовом `apply_edit` / `revert_edit`.

**`entity_resolution.py` — 82% (~30 строк)**

Непокрытые ветки: обработка дубля (вакансия с теми же source_message_id),
race condition при параллельном апдейте одной вакансии (хотя бы happy path),
`_create_vacancy` с `skills=[]` (дефолт) и с непустым списком.

**`batch_processor.py` — 79% (~25 строк)**

Не покрыты: пустой батч (0 сообщений), батч с одним мусорным сообщением,
`mark_processed` при DB-ошибке (проверка что не падает с необработанным исключением).
