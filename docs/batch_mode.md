## 1. Зачем нужен batch-режим

В режиме `per_message` каждое сообщение разбирается сразу как пришло. Проблема: когда приходит
«по питонисту подняли до 350к», бот видит только это сообщение и не знает, к какой именно
вакансии его привязать. Связь угадывается по семантической близости текстов (эмбеддинги), и
здесь случаются ошибки — бот создаёт новую вакансию вместо обновления старой.

Batch-режим решает это иначе: вместо разбора по одному **копим сообщения** и отдаём их LLM
**пачкой — все сразу, в одном контексте**. Модель видит и «открыли питониста», и «подняли до 350»
рядом и сама понимает, что это про одну вакансию. Меньше угадывания — выше точность.

При этом есть исключения, когда ждать пачки не нужно: если у сообщения есть **явная структурная
привязка** к существующей вакансии (тред или цитата), оно обрабатывается немедленно.

## 2. Как включить

В `.env` или переменных окружения:

```
PROCESSING_MODE=batch

# Необязательные параметры (дефолты показаны ниже)
BATCH_SIZE=100          # накопилось столько необработанных → флаш
BATCH_TIMEOUT_SECONDS=300  # сообщение ждёт дольше N секунд → флаш (хвост)
BATCH_POLL_SECONDS=30   # как часто тикер проверяет условия
```

По умолчанию стоит `per_message`. Оба режима живут в одном коде, переключение — одна строка.

## 3. Ключевые концепции и термины

| Термин | Смысл |
|--------|-------|
| **пачка (batch)** | Набор необработанных сообщений одного space, отправляемых LLM в одном запросе |
| **онлайн-ветка** | Немедленная обработка при наличии структурной привязки (тред/цитата) |
| **флаш** | Запуск pipeline для созревшей пачки |
| **тикер** | Фоновая задача, периодически проверяющая условия флаша |
| **структурная привязка** | Явная связь: сообщение является ответом в треде или цитирует другое |
| **is_processed** | Флаг в БД: `true` = разобрано (онлайн-веткой или пачкой), `false` = ждёт |
| **quoted_message_id** | Сохранённый id процитированного сообщения — восстанавливает связь в пачке |
| **thread_label** | Буква (A, B, ...) которой LLM видит группу сообщений одного треда |

## 4. Схема потока данных

```
Google Chat ──► Pub/Sub ──► POST /chat/pubsub-push
                                    │
                                    ├─ [created] ──► persist_message()  ← синхронно, до ACK
                                    │                      │
                                    │               route_created_batch()  ← фоново
                                    │                      │
                                    │               find_anchor_vacancy()
                                    │                  ├─ цитата → по quoted_message_id
                                    │                  └─ тред   → по thread_id
                                    │                      │
                                    │             ┌────────┴────────┐
                                    │             │                 │
                                    │         НАЙДЕНА           НЕ НАЙДЕНА
                                    │             │                 │
                                    │       embed+extract      is_processed=false
                                    │       mark_processed      (ждёт пачки)
                                    │
                                    ├─ [updated] ──► handle_edit_batch()  ← фоново
                                    │                  ├─ is_processed=false → только text+flag
                                    │                  └─ is_processed=true  → полный re-extract
                                    │
                                    └─ [deleted] ──► handle_delete()  ← фоново
                                                       └─ soft-delete / откат полей


batch_ticker()  ────── каждые BATCH_POLL_SECONDS ──────►  flush_due_batches()
                                                                │
                                                    для каждого space:
                                                    cnt ≥ BATCH_SIZE
                                                    OR age ≥ BATCH_TIMEOUT_SECONDS
                                                                │
                                                          flush_batch(space_id)
                                                                │
                                               ┌────────────────────────────────┐
                                               │  _fetch_pending                 │
                                               │  _embed_batch                   │
                                               │  _build_markup (thread labels,  │
                                               │                 reply_to hints) │
                                               │  extract_batch  ◄── один LLM   │
                                               │  _apply_items   ◄── resolve×N  │
                                               │  _mark_processed                │
                                               └────────────────────────────────┘
```

## 5. Шаг 0 — приём и сохранение события

**Файл:** `app/api/pubsub.py`

Endpoint `POST /chat/pubsub-push` разбирает тело Pub/Sub-сообщения и вызывает
`parse_we_event()` → `IncomingMessage`. Первое что происходит — синхронный вызов
`persist_message(incoming)` **до того, как отдан HTTP 200**.

Это намеренно: Pub/Sub считает сообщение необработанным, пока не получит 200. Если упасть до
сохранения, Pub/Sub придёт снова — сообщение будет потеряно. Поэтому сохраняем сначала, ack
потом.

При сохранении в таблицу `chat_messages` пишется в том числе:
- `quoted_message_id` — если событие содержит `quotedMessageMetadata.name`
- `is_processed = false` — по умолчанию

## 6. Шаг 1 — маршрутизация нового сообщения

**Файл:** `app/api/pubsub.py` → `app/services/batch_processor.py::route_created_batch()`

После сохранения добавляется `background_tasks.add_task(route_created_batch, incoming)`.
Это означает «выполни после отправки ответа» — HTTP 200 уйдёт немедленно, не дожидаясь обработки.

`route_created_batch()` делает одно: вызывает `find_anchor_vacancy(msg)`.

### Как работает find_anchor_vacancy

**Файл:** `app/services/entity_resolution.py`

Ищет структурную привязку в порядке убывания приоритета:

**1. Цитата** (`quoted_message_id` заполнен)

```
chat_messages (процитированное)
    → vacancy_revisions.source_message_id
    → vacancies WHERE status != 'closed' AND is_deleted = false
```

Если пользователь процитировал сообщение об открытии вакансии, мы найдём ту вакансию напрямую,
без поиска по смыслу.

**2. Тред** (`thread_id` заполнен)

```
vacancy_revisions WHERE source_message_id IN (
    SELECT id FROM chat_messages WHERE thread_id = ?
)
→ vacancies WHERE status != 'closed' AND is_deleted = false
```

Если в треде уже есть ревизии вакансии, текущее сообщение — продолжение той же темы.

Цитата приоритетнее треда: `quoted_message_id` — более сильный сигнал.

### Что происходит дальше

**Привязка найдена** → онлайн-ветка: сообщение обрабатывается прямо сейчас.

**Привязка не найдена** → функция просто возвращает `None`. `is_processed` остаётся `false`.
Сообщение будет взято тикером в составе пачки.

## 7. Онлайн-ветка: немедленная обработка

**Файл:** `app/services/batch_processor.py::route_created_batch()`

Когда `find_anchor_vacancy()` вернула вакансию:

1. `embed_message(msg)` — считает эмбеддинг сообщения и сохраняет в `chat_messages_embeddings`.
2. `run_extraction(msg)` — одиночный LLM-вызов на это сообщение (как в `per_message`).
3. `mark_processed_message(message_id)` — `UPDATE chat_messages SET is_processed = true`.

Это логируется как `batch_inline_resolved`. Пачка это сообщение не увидит — `_fetch_pending`
выбирает только `is_processed = false`.

**Зачем не просто ждать пачки?** Потому что когда привязка явная, нет смысла копить — и так
понятно, к чему применять. Немедленная обработка даёт более быстрый отклик для thread-reply'ев.

## 8. Фоновый тикер: когда запускается пачка

**Файл:** `app/services/batch_processor.py::batch_ticker()`, `flush_due_batches()`

`batch_ticker()` запускается при старте приложения (в `lifespan`-хуке `app/main.py`):

```python
task = asyncio.create_task(batch_ticker())
```

При завершении приложения `task.cancel()`.

Логика тикера:
```
while True:
    await asyncio.sleep(BATCH_POLL_SECONDS)  # дефолт: 30 сек
    await flush_due_batches()
```

### flush_due_batches: кого флашить

Запрос к БД: для каждого `space_id` — количество необработанных и возраст самого старого:

```sql
SELECT space_id,
       COUNT(*)                       AS cnt,
       MIN(created_at)                AS oldest
FROM chat_messages
WHERE is_processed = false AND is_deleted = false
GROUP BY space_id
```

Для каждого space проверяется:
- `cnt >= BATCH_SIZE` → пачка «полная» по количеству
- `now - oldest >= BATCH_TIMEOUT_SECONDS` → самое старое сообщение ждёт слишком долго

Если хотя бы одно условие выполнено — `flush_batch(space_id)`.

Таймаут нужен, чтобы «хвост» никогда не висел вечно. Даже если в чате только одно сообщение в
день, оно будет разобрано максимум через `BATCH_TIMEOUT_SECONDS` секунд.

### Блокировка параллельных флашей

```python
_lock = asyncio.Lock()

async def flush_batch(space_id):
    async with _lock:
        ...
```

Lock исключает два одновременных флаша для одного space в рамках одного процесса. Для
горизонтального масштабирования (несколько воркеров) потребуется `SELECT ... FOR UPDATE SKIP LOCKED`
на уровне БД — сейчас это явно не реализовано.

## 9. flush_batch: полный pipeline пачки

**Файл:** `app/services/batch_processor.py::flush_batch()`

Полный pipeline для одного space:

### Шаг 9.1 — _fetch_pending

```sql
SELECT * FROM chat_messages
WHERE space_id = ? AND is_processed = false AND is_deleted = false
ORDER BY created_at
LIMIT BATCH_SIZE
```

Сортировка по времени важна: LLM увидит сообщения в хронологическом порядке, что помогает
корректно связывать follow-up'ы.

Частичный индекс `ix_chat_messages_unprocessed` (`WHERE is_processed = false`) делает этот
запрос быстрым даже при большой истории — исторические сообщения (`is_processed = true`) в
индекс не попадают.

### Шаг 9.2 — _embed_batch

Считает эмбеддинги всей пачки за **один вызов OpenAI** (batch embeddings). Идемпотентно:
пропускает сообщения, у которых вектор уже есть в `chat_messages_embeddings`. Это защищает от
двойной траты при retry.

### Шаг 9.3 — _build_markup

Готовит разметку для LLM — дополнительные метки, которые помогают модели понять структуру пачки.

**Thread labels** — буквенные метки (A, B, C, ...) для тредов, встречающихся в пачке два или
более раз:

```
[0] Иван (тред A): ищем питониста
[1] Мария: привет!
[2] Иван (тред A): зп до 350к
[3] Петя (тред B): нужен DevOps
[4] Петя (тред B): удалёнка приветствуется
```

Одиночные сообщения треда метку не получают — она бессмысленна без пары.

**reply_to_index** — индекс в пачке, если процитированное сообщение тоже входит в пачку:

```
[3] Петя (↳ ответ на [0]): уточните стек
```

**reply_to_text** — если процитированное сообщение **не** в пачке (оно уже обработано),
подгружается текст из БД и вставляется явно:

```
[3] Петя (↳ ответ на «ищем питониста, до 300к»): уточните стек
```

Это гарантирует, что LLM всегда понимает контекст цитаты, даже если оригинал вне текущей пачки.

### Шаг 9.4 — extract_batch

Один LLM-вызов на всю пачку. Подробнее — в следующем разделе.

### Шаг 9.5 — _apply_items

Каждый `BatchItem` (результат LLM по одному индексу пачки) оборачивается в `IncomingMessage`
и прогоняется через `resolve_and_save()`. Сообщения с `action == "none"` пропускаются.

### Шаг 9.6 — _mark_processed

```sql
UPDATE chat_messages SET is_processed = true WHERE id IN (...)
```

Помечает **всю пачку** разобранной — включая `action="none"` сообщения (они не про вакансии,
но они обработаны). Только после этого шага тикер больше не возьмёт эти сообщения.

**Важно:** если `flush_batch` упал с исключением на любом из шагов, `_mark_processed` не
вызывается. Пачка остаётся необработанной и будет взята в следующем тике. Это гарантирует
«at-least-once»: лучше обработать дважды (идемпотентность защитит), чем потерять.

## 10. LLM-экстрактор пачки

**Файл:** `app/llm/batch_extractor.py`

### BatchItem

```python
class BatchItem(ExtractionResult):
    message_index: int   # индекс в пачке → знаем, какое сообщение
    # наследует: action, entity_ref, fields, confidence
```

### Системный промпт

Инструктирует LLM разбирать **всю пачку как единый контекст**:

- `create` — новая позиция, которой нет в открытых вакансиях
- `update` — уточнение существующей
- `close` — закрытие позиции
- `none` — не про вакансии, в ответ не включать

Правила привязки follow-up'ов (в порядке убывания приоритета):
1. Явная цитата `[↳ ответ на N]` — сильнейший сигнал
2. Один тред (одна метка, напр. «тред A»)
3. Смысловая близость и соседство в пачке

Запрет: **никогда не привязывать по похожей зарплате** — только по структурному контексту пачки.

При сомнении между `create` и `update` — ставить `update`.

### Формат запроса к LLM

```
Открытые вакансии:
- Backend Engineer (Python, до 300к) [latest]
- DevOps Engineer

Сообщения:
[0] Иван (тред A): ищем питониста в команду бэкенда, зп до 250к
[1] Мария: привет всем!
[2] Иван (тред A): обновляем по питонисту — теперь до 350к
[3] Петя: нужен DevOps, удалёнка
[4] Саша (↳ ответ на [3]): уточните стек
```

### Ответ LLM

```json
[
  {"message_index": 0, "action": "create", "entity_ref": "питонист", "fields": {"title": "Backend (Python)", "salary_max": 250000}, "confidence": 0.92},
  {"message_index": 2, "action": "update", "entity_ref": "питонист", "fields": {"salary_max": 350000}, "confidence": 0.95},
  {"message_index": 3, "action": "create", "entity_ref": "DevOps", "fields": {"title": "DevOps Engineer"}, "confidence": 0.88},
  {"message_index": 4, "action": "update", "entity_ref": "DevOps", "fields": {}, "confidence": 0.7}
]
```

Сообщение [1] («привет всем!») в ответ не включается (`action="none"` молча отбрасывается).

### Retry

До `_MAX_ATTEMPTS = 2` попыток при пустом или битом ответе. При обоих сбоях возвращает `[]` —
пачка остаётся необработанной до следующего тика.

## 11. Применение результатов: resolve_and_save

**Файл:** `app/services/entity_resolution.py`

Каждый `BatchItem` проходит через `resolve_and_save(msg, result)`. Логика:

### Шаг 1 — структурная привязка (снова)

`find_anchor_vacancy(msg)` — та же функция, что и в онлайн-ветке. Нужна здесь, потому что
сообщение может цитировать что-то, что не является частью текущей пачки (обработано ранее).

Если привязка найдена и `action == "create"` — переключается на `update` (не может быть новой
вакансией, если тред/цитата уже к ней привязаны).

### Шаг 2 — поиск по эмбеддингу (если нет структурной привязки)

Берём `entity_ref` от LLM, считаем его эмбеддинг, ищем ближайшие вакансии по cosine-similarity
с порогом `0.75`. При `update/close` и пустом результате — fallback без порога (top-5).

### Шаг 3 — создание или обновление

**Нет кандидатов:**
- `action == "create"` → создаём новую вакансию
- `_decide_new_posting(text)` → если regex или LLM считают это объявлением найма → создаём

**Есть кандидаты — LLM-резолвер** (`resolve_entity`):
- `confidence >= 0.6` + `_decide_new_posting == True` → создаём новую, наследуя `title/team` из похожей
- `confidence >= 0.6` + не новый найм → `update/close` существующей
- Низкая уверенность → ревизия со статусом `pending`
- Полный промах для `update/close` → warning в лог, ничего не меняем

### Запись ревизии

Каждое изменение пишется в `vacancy_revisions` с полями:
- `action` — что сделали
- `changed_field` — какое поле изменилось
- `old_value / new_value` — до и после
- `source_message_id` — id сообщения-источника (для идемпотентности и возможного отката)

## 12. Правки сообщений (updated)

**Файл:** `app/services/edits.py::handle_edit_batch()`

Правка в batch-режиме обрабатывается по-разному в зависимости от состояния сообщения.

### Сообщение ещё не разобрано (is_processed = false)

Сообщение ждёт своей пачки. Пачка ещё не запускалась.

**Что делаем:**
```python
msg.text = new_text
msg.is_edited = True
# is_processed остаётся false
```

Логируется как `edit_queued_for_batch`. Больше ничего. Когда пачка запустится, она возьмёт
сообщение с уже актуальным текстом. Эмбеддинг и экстракция произойдут один раз — по свежему тексту.

**Зачем не обрабатывать сразу?** Ещё неизвестно, к чему относится это сообщение. Нет смысла
делать extraction в одиночку — именно за этим и нужна пачка.

### Сообщение уже разобрано (is_processed = true)

Вакансия по этому сообщению уже создана или обновлена.

**Что делаем:**
1. Обновляем `text`, ставим `is_edited = True`
2. Удаляем старый вектор из `chat_messages_embeddings`
3. Считаем новый эмбеддинг
4. Повторно запускаем `run_extraction` — как в `per_message`

Дублирование ревизий исключает `on_conflict_do_nothing` на `(source_message_id, action)`.

## 13. Удаления сообщений (deleted)

**Файл:** `app/services/edits.py::handle_delete()`

Удаление работает **одинаково в обоих режимах** — в `pubsub.py` нет ветки по `processing_mode`
для `deleted`.

### Шаг 1 — пометить сообщение удалённым

```sql
UPDATE chat_messages SET is_deleted = true WHERE message_id = ?
```

После этого `_fetch_pending` уже не возьмёт его в пачку (фильтр `AND is_deleted = false`).
Если оно ещё не было обработано — просто исчезнет из очереди.

### Шаг 2 — найти затронутые вакансии

```sql
SELECT DISTINCT vacancy_id
FROM vacancy_revisions
WHERE source_message_id = ?
```

Если вакансий нет (сообщение не дало ревизий) — всё, на этом шаге заканчиваем.

### Шаг 3 — для каждой затронутой вакансии

**Случай A: единственный источник или удалено create-сообщение**

Если у вакансии нет других живых (`is_deleted = false`) источников, или удалённое сообщение
создало эту вакансию (ревизия `action = "create"`):

→ Soft-delete: `vacancies.is_deleted = true`

**Случай B: есть другие живые источники и удалено не create**

Вакансия выживает, но нужно откатить изменения, которые внесло удалённое сообщение.

→ `_revert_message_deltas(vacancy, deleted_source_message_id)`

### _revert_message_deltas: как работает откат

Берём все ревизии удалённого сообщения, которые изменили конкретные поля (`changed_field is not null`).

Для каждого такого поля проверяем: **была ли более поздняя живая ревизия, которая поменяла то же
поле?** (через `_fields_changed_after`)

- Если да — не трогаем. Более свежее сообщение уже перезаписало поле, откатывать нечего.
- Если нет — восстанавливаем `old_value` из ревизии удалённого сообщения.

Пример:
```
Ревизия 1 (source=MSG1): salary_max: None → 300000
Ревизия 2 (source=MSG2): salary_max: 300000 → 350000
Ревизия 3 (source=MSG1): team: None → "Backend"

Удаляем MSG1:
- salary_max: MSG2 поменял после → НЕ откатываем (оставляем 350000)
- team: никто не менял после → откатываем в None
```

## 15. Идемпотентность

Система рассчитана на «at-least-once»: одно сообщение может попасть в пайплайн дважды (retry,
повторная доставка Pub/Sub). Несколько механизмов защищают от дублей:

### На уровне БД

```sql
-- Нельзя создать две ревизии с одним source_message_id и одним action
INSERT INTO vacancy_revisions (...) ON CONFLICT DO NOTHING
```

Если `run_extraction` запустится дважды на одном сообщении — вторая ревизия просто не запишется.

### На уровне эмбеддингов

`_embed_batch` проверяет наличие вектора перед вычислением:
```python
already_embedded = {id for id in existing_embeddings}
to_embed = [msg for msg in batch if msg.id not in already_embedded]
```

### На уровне статуса

После успешного `flush_batch` все сообщения помечаются `is_processed = true`. Следующий тик их
не возьмёт. Провал до `_mark_processed` → следующий тик возьмёт снова → ревизии не задублируются
из-за `ON CONFLICT DO NOTHING`.

## 16. Отличия от per_message

| Аспект | per_message | batch |
|--------|-------------|-------|
| Когда обрабатывается | Сразу при получении | Накоплено ≥ batch_size ИЛИ старейшее ≥ timeout |
| Контекст LLM | Одно сообщение | Вся пачка space'а |
| Привязка follow-up'ов | Косвенно, по эмбеддингам | Прямо, по структуре пачки |
| Правки ещё не обработанного | N/A | Только обновляем текст, extraction при флаше |
| Правки уже обработанного | Полный re-extract | То же самое |
| Удаления | handle_delete | handle_delete (одинаков) |
| Thread/цитата при новом сообщении | run_extraction сразу | find_anchor → online-ветка (немедленно) или ждёт пачки |
| Эмбеддинги | Сразу при получении | Пачкой при флаше (или сразу в онлайн-ветке) |

**Когда использовать per_message:** небольшой чат, мало follow-up'ов, важна моментальная реакция.

**Когда использовать batch:** активный чат, много цепочек обсуждений, нужна точность связывания.
