# E2E-план: боевая проверка сбора данных + RAG-чата

> Цель документа — пошагово поднять **оригинальную** (не тестовую) БД и в боевых
> условиях (реальные LLM + эмбеддинги + реальный пайплайн) проверить два контура:
> **(A) сбор данных** (приём сообщений → пачка → извлечение/нормализация вакансий)
> и **(B) RAG-чат** (вопрос пользователя → интент → аналитика/RAG → ответ).
>
> «Боевые условия» здесь = весь прод-код по своему настоящему пути, с настоящими
> моделями (Gemini через OpenRouter + OpenAI embeddings) и настоящей БД. Отличие
> от полного прода — сообщения подаём сами (HTTP-эмуляция Pub/Sub-конверта), а не
> ждём доставки от Google. Полную интеграцию с Google Chat выносим в опц. часть C.

---

## 0. Критерии успеха (что считаем «работает»)

| Контур | Успех | Провал |
|---|---|---|
| Сбор данных | `pending → 0`, `failed = 0`, число вакансий ≈ числу реальных объявлений; апдейты/закрытия отразились; новые оси (`company`/`seniority`/`role_category`/`skills`) заполнены осмысленно | остались `pending`, есть `failed` (ядовитые), дубли вакансий, апдейт создал новую вакансию вместо правки |
| RAG-чат | ответ опирается на БД (актуальный статус/зп), цифры совпадают с SQL, нет галлюцинаций, «нет данных» честно сообщается | ответ противоречит БД, выдумывает вакансии, падает в `try/except` («что-то пошло не так») |

Замеры фиксируем в конце (раздел 9 — чек-лист приёмки).

## 1. Предусловия

- **Docker Desktop** запущен (БД и redis поднимаются из `docker-compose.yml`).
- **venv** активирован, зависимости стоят (`pip install -r requirements.txt`).
- **`.env`** с РЕАЛЬНЫМИ ключами (это боевой прогон — LLM/эмбеддинги ходят в сеть и
  стоят денег). Шаблон — `.env.example`. Критичные строки:
  ```ini
  DATABASE_URL=postgresql+asyncpg://postgres:password@localhost:5432/chatbot
  OPENAI_API_KEY=sk-...            # реальный — для эмбеддингов
  OPENROUTER_API_KEY=sk-or-...     # реальный — для всех LLM-задач
  SKIP_JWT_VALIDATION=true         # локально без Google-токенов (см. ниже)
  APP_BASE_URL=http://localhost:8000   # для части C заменить на ngrok-URL
  ```
  > ⚠️ Модели и режим уже прописаны в `app/config.py` по итогам eval: `processing_mode=batch`,
  > извлечение/резолв/ответ — `google/gemini-3.1-flash-lite`. Менять не нужно.
  > `.env` в `.gitignore` — живые ключи НЕ коммитим.

- **`SKIP_JWT_VALIDATION=true`** обязательно для локального прогона: иначе и
  `/chat/pubsub-push`, и `/chat/interaction` потребуют валидный Google OIDC-токен
  (`app/api/pubsub.py`, `app/api/interactions.py`). С ним обе ручки принимают сырой
  HTTP без подписи — ровно то, что нужно для эмуляции.

## 2. Карта потоков (что именно проверяем)

```
СБОР ДАННЫХ (контур A):
  Pub/Sub-конверт ──HTTP──▶ POST /chat/pubsub-push (app/api/pubsub.py)
    │  parse_we_event → IncomingMessage
    ├─ created  → persist_message (синхронно, до ack)
    │              └─ batch: route_created_batch (онлайн только при структурной
    │                 привязке к существующей вакансии: тред/цитата); иначе ждёт пачку
    ├─ updated  → handle_edit_batch (правка существующей вакансии)
    └─ deleted  → handle_delete
                          │
  batch_ticker (фон, каждые batch_poll_seconds=15с) ──▶ flush_due_batches
    триггеры флаша: тишина quiet_seconds=75с | batch_size=15 | timeout=300с
                          │
    flush_batch(space) → batch_extractor (Gemini, один большой контекст)
      → нормализация (skill/company/seniority/role) → entity_resolution
      → vacancies + vacancy_revisions (идемпотентно по source_message_id+action)

RAG-ЧАТ (контур B):
  MESSAGE-событие ──HTTP──▶ POST /chat/interaction (app/api/interactions.py)
    │  resume? → match_resume
    └─ handle_query → classify_intent (Gemini)
         ├─ count/list_recent/chart/salary_chart → app/services/analytics.py
         ├─ skill_demand/trends → app/services/trends.py
         ├─ salary_by_company/role_matrix → app/services/clusters.py
         └─ search (fallback) → build_rag_context (pgvector) → generate_answer (Gemini)
```

## 5. Часть A — боевой тест сбора данных

### A1. Базовый прогон (готовый нагрузочник)

`scripts/load_test.py` генерит ~100 реалистичных событий (25 объявлений + треды +
цитаты + правки + закрытия + мусор), шлёт их Pub/Sub-конвертом на работающее
приложение и мониторит разбор до `pending=0`.

```bash
python -m scripts.load_test --url http://localhost:8000 --timeout 600
```

Что увидишь: построчный мониторинг `pending/processed/failed/vacancies` и финальный
вердикт. **Ожидаемо:** `pending=0`, `failed=0`, `vacancies` в районе 25 (± за счёт
дедупа похожих и привязки follow-up'ов).

> Тикер сам флашит по тишине (75с) — после отправки просто жди, мониторинг покажет
> прогресс. Не хочешь ждать — форсни флаш (A3).

### A2. Кейсы, которые проверяем (и как читать результат)

`load_test` уже закладывает их в `build_events()`. После прогона разбери диагностикой:

```bash
python -m scripts.load_test --diagnose
```

| Кейс | Что заложено | Ожидаемое поведение | Как проверить |
|---|---|---|---|
| **Создание** | 25 независимых объявлений ролей | 25 вакансий, ревизия `create` у каждой | в `--diagnose` блок «Ревизии по action» → `create ≈ 25` |
| **Апдейт** | 8 `updated`-событий тех же сообщений («вилку подняли») | НЕ новые вакансии, а ревизия `update` с `changed_field=salary_*` | `update`-ревизии привязаны к существующим вакансиям, число вакансий не выросло |
| **Закрытие** | 7 «Закрыли вакансию … вышел кандидат» | статус → `closed`, ревизия `close` | `show_vacancies` → статус `closed` у этих ролей |
| **Тред-follow-up** | 12 тредов: объявление + реплай без названия | follow-up привязан к вакансии из своего треда | `--diagnose`: follow-up в той же вакансии |
| **Цитата** | 8: объявление + quoted reply без названия | follow-up привязан к процитированной вакансии | `--diagnose` |
| **Мусор** | 5 бытовых сообщений | НЕ создают вакансий, остаются без ревизий | блок «Сообщения без ревизий» → там мусор, `process_status=processed` |
| **Похожие названия** | много ролей-разработчиков | не схлопываются в одну (Python ≠ Go ≠ Java) | число вакансий не «усохло» |

### A3. Ручной флаш и точечная инспекция

# Принудительно разобрать всё, что ждёт пачку (если не хочешь ждать тикер)
python -m scripts.run_batch

# Полный список вакансий + история ревизий каждой
python -m scripts.show_vacancies

# Контекстная привязка follow-up'ов (тред/цитата/упоминание/голый) — отдельный сценарий
python -m scripts.test_context

### A4. Проверка качества новых осей (критичный путь — недавно добавлен)

`load_test` слабо нагружает `company`/`skills` (роли без работодателя). Чтобы
по-боевому проверить извлечение/нормализацию новых полей, отправь руками 5-10
насыщенных сообщений и проверь колонки. Примеры «боевых» сообщений (подавай как
created-события — см. формат конверта в `_envelope`/раздел 6):

- `«Avito ищет senior Python backend, стек: FastAPI, PostgreSQL, Kafka, до 400k, удалёнка»`
  → company=`avito`, seniority=`senior`, role_category=`backend`, skills=`[python, fastapi, postgresql, kafka]`
- `«Тинькофф: middle data engineer, Spark/Airflow, Москва, гибрид»`
  → company=`tinkoff`, seniority=`middle`, role_category=`data`, skills=`[spark, airflow]`
- `«Берём джуна на фронт, React + TypeScript, можно без опыта»`
  → seniority=`junior`, role_category=`frontend`, skills=`[react, typescript]`
- Путалки: `«питонист»` vs `«python-разработчик»` (нормализатор должен свести стек к `python`).

Проверка SQL (новые оси заполнены и нормализованы):

```sql
-- что извлеклось по новым осям
SELECT title, company, seniority, role_category, skills
FROM vacancies WHERE is_deleted = false ORDER BY created_at DESC LIMIT 20;

-- сколько вакансий вообще получили нормализованные оси (доля заполнения)
SELECT
  count(*) AS total,
  count(company) AS with_company,
  count(seniority) AS with_seniority,
  count(role_category) AS with_role,
  count(*) FILTER (WHERE skills <> '{}') AS with_skills
FROM vacancies WHERE is_deleted = false;
```

**Что считаем успехом:** оси заполнены там, где сигнал в тексте был; нормализация
свела синонимы (`питон/py/python → python`, `сеньор/senior → senior`); пустые там,
где данных не было (NULL/`{}`, а не мусор).

### A5. Злые/граничные кейсы (устойчивость пайплайна)

| Кейс | Как воспроизвести | Ожидаемое |
|---|---|---|
| **Дубль доставки** | отправить то же `created` дважды (Pub/Sub at-least-once) | `persist_message` идемпотентен → второй раз не дублирует; ревизии идемпотентны по `(source_message_id, action)` |
| **Правка во время флаша** | `updated` сразу после `created`, до разбора | условный `mark_processed` по `text_hash` не проглотит правку (batch v2, B1) |
| **Ядовитое сообщение** | отправить заведомо ломающий payload (если найдётся) | пачка бисектится при `flush_attempts≥3`, одиночный уходит в `failed` при `≥5` — НЕ блокирует остальные |
| **Удаление** | `deleted`-событие на существующее сообщение | `handle_delete`, сообщение `is_deleted=true`, из аналитики выпадает |
| **Кривой JSON** | битый конверт | ручка отвечает 204 (ack), не 500 — Pub/Sub не зациклит редоставку |

Сводный SQL-светофор после прогона:

```sql
SELECT process_status, count(*) FROM chat_messages
WHERE space_id = 'spaces/LOADTEST' GROUP BY process_status;
-- ждём: processed = N, pending = 0, failed = 0
```

## 6. Формат события (для ручной подачи кейсов A4/A5)

Ручка `/chat/pubsub-push` ждёт Pub/Sub push-конверт: тело события — base64 в
`message.data`, тип — в `message.attributes.ce-type`. Готовая сборка — функция
`_envelope()` в `scripts/load_test.py`. Минимальный пример (Python, реюз отправщика):

```python
import asyncio, base64, json
from datetime import datetime, timezone
import httpx

SPACE = "spaces/LOADTEST"
def envelope(mid, text, *, ce="created", thread=None, quoted=None):
    msg = {"name": mid, "text": text,
           "createTime": datetime.now(timezone.utc).isoformat(),
           "space": {"name": SPACE},
           "sender": {"name": "users/me", "displayName": "Я"}}
    if thread:  msg["thread"] = {"name": thread}
    if quoted:  msg["quotedMessageMetadata"] = {"name": quoted}
    return {"message": {
        "data": base64.b64encode(json.dumps({"message": msg}).encode()).decode(),
        "messageId": mid,
        "attributes": {"ce-type": f"google.workspace.chat.message.v1.{ce}"}}}

async def main():
    async with httpx.AsyncClient() as c:
        r = await c.post("http://localhost:8000/chat/pubsub-push",
            json=envelope("spaces/LOADTEST/messages/x1",
                          "Avito ищет senior Python backend, FastAPI+Kafka, до 400k"))
        print(r.status_code)  # 204
asyncio.run(main())
```

Затем подожди тишину (75с) или `python -m scripts.run_batch`, и проверь SQL из A4.

## 7. Часть B — боевой тест RAG-чата

Предусловие: контур A отработал, в БД лежат вакансии (с осями). Чат дёргаем через
`/chat/interaction` MESSAGE-событием (формат Google Chat). При `SKIP_JWT_VALIDATION=true`
подпись не нужна.

### B1. Как отправить вопрос

```bash
curl -s -X POST http://localhost:8000/chat/interaction \
  -H "Content-Type: application/json" \
  -d '{
    "type": "MESSAGE",
    "user": {"name": "users/kirill"},
    "space": {"name": "spaces/LOADTEST"},
    "message": {"text": "сколько открытых вакансий по python"}
  }'
# Ответ: {"text": "..."} либо {"cardsV2": [...]} (для графиков)
```

### B2. Матрица вопросов по интентам (минимум по одному на каждый)

| Вопрос | Ожидаемый интент | Что проверить в ответе |
|---|---|---|
| «сколько открытых вакансий» | `count` | число совпадает с `SELECT count(*) ... status!='closed'` |
| «сколько по python за неделю» | `count` (topic+days) | фильтр по теме и периоду применился |
| «что добавили за 3 дня» | `list_recent` | список свежих, с датами/зп |
| «график по командам» | `chart` | карточка или текстовый fallback с командами |
| «график зарплат» | `salary_chart` | вакансии с вилками |
| «какие технологии в топе» | `skill_demand` | топ навыков из `skills[]` |
| «что выходит из моды» | `skill_demand` (least) | хвост спроса |
| «какие технологии набирают популярность» | `trends` | растущие/падающие м-к-м |
| «сколько платят по компаниям» | `salary_by_company` | медиана по `company` |
| «зарплаты по специальностям и грейдам» | `role_matrix` | `role_category × seniority` |
| «открыта ли вакансия питониста» | `search` (RAG) | ответ опирается на статус из БД |
| «расскажи про DevOps-позицию» | `search` (RAG) | детали из карточки вакансии, не выдумка |

> Сверяй каждое число с прямым SQL — это и есть проверка «опоры на БД».
> classify_intent на Gemini может иногда промахнуться интентом — несколько
> переформулировок на интент допустимы; систематический промах фиксируй.

### B3. Контекст и диалог

| Кейс | Как | Ожидаемое |
|---|---|---|
| **Память диалога** | задать 2-3 вопроса подряд от одного `user.name`, затем уточняющий («а по ней что со сроками?») | в `build_rag_context` подтягивается `running_summary`/`recent_turns`; ответ учитывает предыдущие реплики |
| **Свёртка** | задать ≥ `MAX_TURNS` реплик | старое сворачивается в `running_summary` (фон `compact_conversation`) |
| **Резюме текстом** | `"резюме: Python, 5 лет, FastAPI, Postgres"` | `match_resume` → подбор вакансий по skills |
| **Резюме файлом** | вложение PDF/DOCX | `extract_text_from_attachments` → подбор; неподдерживаемый файл → честная подсказка |
| **Приоритет источника** | вакансия закрыта в БД, но в старом сообщении «открыта» | ответ верит БД (закрыта), не сообщению (промпт answerer это требует) |

### B4. Негативные кейсы

| Вопрос/ситуация | Ожидаемое |
|---|---|
| Вопрос по несуществующей роли («есть вакансия космонавта?») | честное «не нашёл», без выдумки |
| Пустая БД (если гоняешь до части A) | «нет данных»/«недостаточно данных», не падение |
| LLM/сеть упала | `_handle_search` ловит исключение → «Извини, что-то пошло не так» (в логах `interaction_rag_failed`) |

### B5. Сверка с БД (примеры контрольных запросов)

```sql
-- проверить ответ count
SELECT count(*) FROM vacancies WHERE is_deleted=false AND status<>'closed';
-- проверить salary_by_company
SELECT company, percentile_cont(0.5) WITHIN GROUP (ORDER BY salary_max) med
FROM vacancies WHERE is_deleted=false AND company IS NOT NULL GROUP BY company;
```

## 9. Чек-лист приёмки

Сбор данных:
- [ ] `load_test`: `pending=0`, `failed=0`
- [ ] число вакансий ≈ числу объявлений (нет дублей/схлопывания)
- [ ] апдейты дали `update`-ревизии, а не новые вакансии
- [ ] закрытия перевели статус в `closed`
- [ ] follow-up'ы (тред/цитата) привязались к верным вакансиям (`test_context`)
- [ ] мусор не породил вакансий
- [ ] новые оси (`company/seniority/role_category/skills`) заполнены и нормализованы (A4)
- [ ] злые кейсы не уронили пайплайн в 500 / не оставили `failed` (A5)

RAG-чат:
- [ ] каждый интент из B2 отрабатывает, числа сходятся с SQL
- [ ] RAG-ответ опирается на актуальный статус из БД (B3 приоритет источника)
- [ ] память диалога подтягивается
- [ ] негативные кейсы дают честный ответ, не галлюцинацию (B4)
- [ ] в логах нет `interaction_rag_failed`

### 13.3. ⚠️ Важное уточнение по метрике «вакансий: 57»

Финальный счётчик `load_test` показал `вакансий: 57` — и это **вводит в заблуждение**.
Скрипт считает их запросом `count(*)` по джойну `vacancies × vacancy_revisions ×
chat_messages`, то есть фактически считает **строки-ревизии**, а не уникальные вакансии.
Разбивка по действиям из `--diagnose`: `create 25 + update 25 + close 7 = 57`.

**Реальное число вакансий = число `create`-ревизий = 25.** Это баг измерения в самом
скрипте (см. бэклог §13.7), а не в пайплайне. Проверочный запрос даёт честное число:

```sql
SELECT count(DISTINCT v.id)
FROM vacancies v
JOIN vacancy_revisions r ON r.vacancy_id = v.id
JOIN chat_messages m ON m.id = r.source_message_id
WHERE m.space_id = 'spaces/LOADTEST' AND v.is_deleted = false;
-- → 25
```

ролей (Python/Go/Frontend/DevOps/ML/QA/системный аналитик/UX), про которые приходило
по 2–3 сообщения. Система **схлопнула спорные в одну вакансию на роль**, а не наплодила
дублей-фантомов — именно тот риск, которого мы боялись, и он НЕ реализовался.

### 13.5. 🐞 Найденная проблема: потеря апдейта из правки сообщения

**Симптом.** 8 сообщений вида `«Поправка по X: вилку подняли до N k»` (это
`updated`-события исходных объявлений `ann-0..7`) ушли в блок «Сообщения без ревизий».
То есть **повышение зарплаты из правки не применилось** — у этих 8 ролей `salary_max`
остался пустым (вакансию им создал тред-месседж «Ищем ещё одного X», в котором зарплаты
не было, а несущая зарплату «Поправка» — потерялась).

**Корневая причина (пошагово).** Сообщение `«Поправка по Python: вилку подняли до 350k»`
проходит через [`resolve_and_save`](../app/services/entity_resolution.py#L196-L223):

1. У него нет структурного якоря (не реплай в тред, не цитата) → прямая привязка мимо.
2. По `entity_ref="Python-разработчик"` ищем кандидатов среди открытых вакансий.
3. **В момент разбора вакансии «Python-разработчик» ещё не существует.** Тайминги:
   у `ann-0` время `ts=1`, у тред-создателя `«Ищем ещё одного Python»` — `ts=26`.
   Пачки разбираются по возрастанию `created_at`, значит «Поправка» (ts1) попала в
   **более раннюю** пачку, чем тред (ts26). Кандидатов — ноль.
4. Код проверяет `_decide_new_posting`: «это объявление о найме?». «Поправка… вилку
   подняли» — не найм, а правка → `False`.
5. → `logger.warning("resolution_no_candidates_for_update")` и `return None`. Ревизия
   НЕ пишется. При этом в [`_apply_items`](../app/services/batch_processor.py#L488-L490)
   сообщение всё равно метится `processed` → уходит в «без ревизий», а не остаётся
   pending на повтор. Апдейт теряется молча для данных, но в логах след есть.

**Почему это вылезло именно в нагрузочнике.** Все 77 событий прилетают за пару секунд,
а первый флаш — позже (по тишине 75с / тикеру). Значит `ann-0` успел стать «Поправкой»
ещё **до первого разбора**: исходный текст «Открыли вакансию Python, до 300k» вообще
никогда не дошёл до создания вакансии — его перезаписала правка. А вакансию потом создал
тред — без зарплаты. То есть здесь сошлись два усиливающих фактора синтетики:
(а) правка пришла раньше, чем что-либо успело обработаться; (б) `updated` отредактировал
**само объявление** в «корректировку», уничтожив исходный текст.

**Насколько это страшно — severity: НИЗКАЯ-СРЕДНЯЯ.**
- В боевом чате (5–10 сообщений/день) правка обычно приходит **отдельным реплаем**
  («подняли вилку до 350k» в тред/цитатой) — а такие у нас привязались все 20/20.
- Чтобы воспроизвести потерю, нужно: запостить объявление → **отредактировать само это
  сообщение** в «Поправку» → и всё это до флаша (тишина 75с). В реальном потоке редко.
- Промах **уже логируется** (`resolution_no_candidates_for_update`) — не совсем немой.
- Это **не угроза стабильности** (ничего не падает, не залипает), только точечная
  неполнота данных в редком сценарии.

### 13.6. Что можно сделать — варианты и нужно ли

> На момент записи ядро НЕ меняем (сознательное решение — сначала зафиксировать факты).
> Ниже — варианты на будущее, от ленивого к основательному.

**Вариант 1 — принять и задокументировать (минимум, рекомендуется).**
Зафиксировать как known-issue: «`update`, чей целевой объект ещё не создан, дропается
и метится processed; воспроизводимо при edit-into-correction до первого флаша».
Стоимость — ноль кода. Честно отражает реальный (низкий) риск.

**Вариант 2 — bounded-retry для непривязанных апдейтов (правильный, средний риск).**
Сейчас непривязанный `update`/`close` метится `processed` и больше не повторяется.
Идея: вместо этого **не метить processed**, оставлять `pending` с инкрементом
`flush_attempts` — тогда следующий флаш, уже после создания целевой вакансии,
до-привяжет апдейт. От зацикливания страхует существующий dead-letter
(`fail_threshold=5` → `failed`).
- Плюс: само-чинит **реалистичный** кейс (create и update разъехались по разным флашам
  в нормальном порядке: создание раньше правки).
- Минус/нюанс: **именно синтетический кейс из §13.5 retry НЕ вылечит** — там update
  *старше* своего create (ts1 < ts26), поэтому и при повторе он снова разбирается
  раньше создания. Для него помогло бы только переупорядочивание или create-on-miss.
- Реализация затрагивает `resolve_and_save` (сигнал «не смог, верни на повтор») →
  `_apply_one` → `_apply_items` (не добавлять в `ok`). Небольшая, но в чувствительном
  месте — нужен аккуратный тест.

**Вариант 3 — create-on-miss (НЕ рекомендуется).**
Создавать новую вакансию из непривязанного апдейта. Это вернёт риск фантомов — ровно
то, чего мы избегали. Не делать.

**Рекомендация.** Сделать **(1) сейчас** (этот раздел уже её закрывает) и
держать **(2) в бэклоге** как улучшение устойчивости, если в боевом логе начнут
всплывать `resolution_no_candidates_for_update`. Create-on-miss не трогать.

### 13.7. Побочные находки (в бэклог, не блокеры)

- **`load_test._stats` меряет ревизии, а не вакансии.** Счётчик «вакансий» считает
  `count(*)` по джойну с ревизиями. Починка: `count(DISTINCT v.id)`. Косметика, но
  путает при чтении итога (мы из-за неё сначала решили, что 57 вакансий вместо 25).
- **8 правок `«Поправка по X»` + 7 цитат `«Открыли позицию X срочно»` без ревизий** —
  ожидаемое поведение дедупа/таймингов (см. §13.5), не баг, но стоит держать в уме
  при чтении `--diagnose`.
