## Гипотеза

Если давать LLM **сразу пачку сообщений в одном контексте** (≈100 штук), она
точнее свяжет «что к чему относится» (follow-up'ы, обновления, новые вакансии),
чем текущий разбор по одному сообщению + слепой матчинг через эмбеддинги в
`entity_resolution`. Текущий per-message режим остаётся рабочим и дефолтным.

## Стратегия отката (два уровня)

1. **Git:** вся работа в ветке `feature/batch-pipeline`. Полный откат к текущему

2. **Runtime:** фича-флаг `PROCESSING_MODE` (дефолт `per_message`). Даже на ветке

## Архитектура: два конвейера

Обработка делится по **природе сигнала**:

**Конвейер 1 — семантический батч** (основная идея).
Новые сообщения **без явной структурной привязки** копятся и раз в
`BATCH_SIZE`/таймаут уходят **одним большим LLM-запросом**, где модель сама
распределяет действия по вакансиям, видя весь контекст пачки + открытые вакансии
из БД.

**Конвейер 2 — структурный/событийный** (мгновенно, без большого LLM).
Сообщения с **надёжным структурным сигналом** (reply в тред или цитата к
**уже существующей** вакансии), а также правки и удаления — обрабатываются сразу
текущим per-message путём.

### Принцип маршрутизации (официант на входе)

На каждое входящее `created`-сообщение в batch-режиме задаётся один вопрос:

> Есть ли у сообщения структурная привязка к вакансии, которая **уже есть в БД**?
> (цитата → `_find_quoted_vacancy`, тред → `_find_thread_vacancy`)

- **Да** → обработать сразу старым путём (мы и так знаем, к чему относится).
- **Нет** → оставить лежать (`is_processed=false`), пачка заберёт позже.

Это автоматически решает «гонку порядка»: follow-up к ещё не созданной вакансии
не имеет anchor'а → едет в ту же пачку, что и его родитель, где LLM их свяжет.

## Цитаты и треды — обрабатываются грамотно и симметрично

Оба структурных сигнала работают по одному механизму. Цитата приоритетнее треда
(как уже сделано в `resolve_and_save`).

**Что даёт сохранение `quoted_message_id` в БД** (сейчас оно теряется при
`persist_message`) — одна колонка закрывает три места разом:

1. **resolve_and_save из пачки.** При обработке пачки мы пересобираем
   `IncomingMessage` из строки БД — теперь с `quoted_message_id`. Значит
   `resolve_and_save` сделает quoted-anchor так же, как в онлайне.
2. **Официант на входе.** Может проверить anchor по цитате и решить «сразу или в
   пачку» (см. принцип маршрутизации).
3. **batch_extractor.** Покажет связь LLM прямо в промпте: «сообщение №5 — ответ
   на сообщение №2» (если процитированное в пачке) или «↳ в ответ на: "<текст>"»
   (если процитированное вне пачки — подтянем текст из БД).

| Сигнал | В онлайне (конвейер 2) | В пачке (конвейер 1) |
|--------|------------------------|----------------------|
| Тред (`thread_id`) | thread-anchor сразу | разметка тредов в промпте + thread-anchor в resolve |
| Цитата (`quoted_message_id`) | quoted-anchor сразу | разметка цитат в промпте + quoted-anchor в resolve |

## Изменения в БД (миграция `0003_batch_processing`)

Таблица `chat_messages`, два аддитивных столбца + индекс:

1. **`is_processed BOOLEAN NOT NULL DEFAULT false`** — флаг «сообщение уже разобрано
   пайплайном». Батч выбирает `false`, обрабатывает, ставит `true`. Без него батч
   не знает, что брать в пачку, и плодит дубли.
   - **Бэкфилл `= true`** для всех существующих строк: они уже разобраны старым
     путём, иначе при включении batch-режима пачка перемелет всю историю.
   - **Частичный индекс** `WHERE is_processed = false` — быстрая выборка
     необработанного «горячего хвоста» без скана всей таблицы.
2. **`quoted_message_id TEXT NULL`** — resource name процитированного сообщения.
   Сейчас приходит в `IncomingMessage`, но в БД не пишется. Старые строки → NULL
   (история, не важно).

Изменение аддитивное: per-message путь эти поля не читает, влияния ноль.
`downgrade` удаляет столбцы и индекс.

## Поток данных (batch-режим)

```
Google присылает сообщение
        │
        ▼
[Официант] pubsub.py
   persist_message → в БД (is_processed=false, +quoted_message_id)
        │
   anchor к существующей вакансии? (цитата/тред)
        ├── да ──► обработать сразу (старый путь) → is_processed=true
        └── нет ─► лежит, ждёт пачку
                        ┊
[Будильник] тикер в lifespan, каждые BATCH_POLL_SECONDS
        │  зовёт →
        ▼
[Повар] flush_due_batches: созрело? (≥BATCH_SIZE или старше таймаута)
        │ да
        ▼
[Повар] flush_batch(space):
   выбрать pending (is_processed=false AND is_deleted=false)
   → батч-эмбеддинги одним вызовом OpenAI
   → batch_extract (большой контекст: треды + цитаты + open vacancies)
   → каждый результат через resolve_and_save
   → пометить is_processed=true
```

## Пошаговый план

### Шаг 1 — Конфиг ([config.py](app/config.py))
- `PROCESSING_MODE: "per_message" | "batch"` (дефолт `per_message`)
- `BATCH_SIZE=100`, `BATCH_TIMEOUT_SECONDS=300`, `BATCH_POLL_SECONDS=30`
- **Проверка:** приложение стартует, читает `.env`.

### Шаг 2 — Миграция `0003` + модель + persist
- Миграция: `is_processed` (+ бэкфилл true, частичный индекс) и `quoted_message_id`.
- [models.py](app/db/models.py): два поля в `ChatMessage` + индекс.
- [ingest.py](app/services/ingest.py) `persist_message`: сохранять `quoted_message_id`.
- **Проверка:** `alembic upgrade head` проходит (когда поднята БД); колонки видны в psql.

### Шаг 3 — Anchor-helper ([entity_resolution.py](app/services/entity_resolution.py))
- Вынести в публичный helper `find_anchor_vacancy(msg) -> uuid | None`
  логику quoted+thread (сейчас она внутри `resolve_and_save`, строки 123-130).
- `resolve_and_save` переиспользует helper (убираем дублирование).
- Helper нужен официанту (шаг 7) для решения «сразу или в пачку».
- **Проверка:** существующие тесты резолюции зелёные (поведение не изменилось).

### Шаг 4 — `app/llm/batch_extractor.py` (новый, ядро гипотезы)
- Вход: список сообщений по порядку с разметкой (треды + цитаты) + open vacancies.
- Один промпт: «выдели ВСЕ действия по вакансиям; follow-up'ы группируй; для
  каждого укажи индекс сообщения-источника; учитывай треды/цитаты и открытые
  вакансии».
- Выход: `list[(message_index, ExtractionResult)]` — переиспользуем `ExtractionResult`.
- **Проверка:** unit-тест с моком LLM (парсинг списка, группировка follow-up'ов).

### Шаг 5 — `app/services/batch_processor.py` (новый, оркестрация)
- `flush_batch(space_id)` под `asyncio.Lock`:
  выбрать pending (`is_processed=false AND is_deleted=false`, `FOR UPDATE SKIP
  LOCKED`, лимит `BATCH_SIZE`, по `created_at`) → разрешить цитаты (индекс в пачке
  или подтянуть текст) → батч-эмбеддинги → `batch_extract` → каждый результат
  через `resolve_and_save` (пересобрав `IncomingMessage` из строки БД) → пометить
  `is_processed=true`.
- `flush_due_batches()`: найти space, где `count>=BATCH_SIZE` ИЛИ `oldest pending`
  старше `BATCH_TIMEOUT_SECONDS`; для каждого вызвать `flush_batch`.
- **Проверка:** тест — pending помечаются обработанными; `resolve_and_save` вызван
  на каждый не-none результат (моки).

### Шаг 6 — Тикер в lifespan ([main.py](app/main.py))
- Если `PROCESSING_MODE=batch` → фоновый цикл (по образцу `renewal_task`):
  `sleep(BATCH_POLL_SECONDS)` → `flush_due_batches()`. Корректная остановка при
  shutdown.
- **Проверка:** лог флаша по таймауту при <BATCH_SIZE сообщений.

### Шаг 7 — Маршрутизация ([pubsub.py](app/api/pubsub.py))
- `per_message` → **всё как сейчас, не трогаю**.
- `batch`:
  - `created`: `persist_message`; `find_anchor_vacancy` → есть → старый путь сразу
    (+`is_processed=true`); нет → ничего (ждёт пачку).
  - `updated`: если `is_processed=false` → обновить только текст (пачка разберёт
    свежий); если `true` → как сейчас (`handle_edit`).
  - `deleted`: как сейчас (`handle_delete`; батч и так фильтрует `is_deleted`).
- **Проверка:** тесты роутинга (anchor → онлайн, без anchor → пачка, режимы).

### Шаг 8 — Тесты
- batch_extractor (парсинг, группировка, треды/цитаты в промпте).
- flush (триггеры count/timeout, пометка is_processed, разрешение цитат).
- маршрутизация (anchor → онлайн, без anchor → пачка; updated/deleted с учётом
  is_processed).
- **Проверка:** `pytest -q` зелёный, без регрессий.
