# Отчёт о работе: batch-режим обработки сообщений

## 1. Контекст: над чем работали

Проект — чат-бот для вакансий. В рабочий чат люди пишут сообщения вроде
«Открыли вакансию питониста, до 300k», «по питонисту подняли до 350», «закрыли
позицию». Бот читает эти сообщения и сам ведёт базу вакансий: создаёт новые,
обновляет условия, закрывает закрытые.

**Как было раньше (режим `per_message`):** каждое сообщение обрабатывается
по-одному, сразу как пришло. Проблема — когда приходит «по питонисту подняли до
350», бот видит только это одно сообщение и не знает, *к какой* вакансии его
привязать. Связь приходится угадывать задним числом по «похожести» текстов
(через эмбеддинги — числовые отпечатки смысла), и тут случаются ошибки: бот
заводит новую вакансию вместо обновления старой.

**Что сделали (новый режим `batch`):** вместо разбора по-одному копим сообщения
и отдаём их нейросети (LLM) **пачкой — все сразу, в одном контексте**. Тогда
модель видит и «открыли питониста», и «подняли до 350» рядом, и сама понимает,
что это про одну вакансию. Меньше угадывания — выше точность. Это и есть главная
гипотеза, которую проверяли.

Важно: старый режим никуда не делся. Новый включается **флагом** (одной
настройкой `PROCESSING_MODE=batch`), по умолчанию работает старый. Это позволяет
безопасно пробовать новое и в любой момент откатиться.

---

## 2. Как устроен batch-режим (два «конвейера»)

Обработка делится по типу сигнала — для наглядности аналогия с кухней ресторана:

**Конвейер 1 — пачка (повар готовит партиями).**
Новые сообщения, по которым непонятно «что к чему», копятся. Когда накопилось
много (по умолчанию настраиваемый порог) **или** прошло достаточно времени —
вся пачка уходит в один большой запрос к LLM, которая распределяет действия по
вакансиям.

**Конвейер 2 — фоновая обработка (официант отдаёт сразу понятное).**
Если у сообщения есть **явная привязка** к уже существующей вакансии — его не
нужно ждать в пачке, обрабатываем сразу. Явная привязка это:
- **тред** — сообщение-ответ в той же ветке обсуждения, что и вакансия;
- **цитата** — пользователь прямо процитировал сообщение, относящееся к вакансии.

Сюда же относятся **правки** и **удаления** сообщений — они всегда
обрабатываются сразу (фоном), а не копятся.

**Будильник (тикер).** Чтобы пачка не висела вечно, если сообщений мало,
фоновый «будильник» раз в N секунд проверяет: не пора ли разобрать накопленное
(по количеству или по времени).

## 3. Что конкретно реализовали в коде

- **Флаг и настройки** — `PROCESSING_MODE` (per_message / batch) и параметры
  пачки: размер, таймаут, частота проверки будильника.
- **Миграция базы `0003`** — добавили в таблицу сообщений два столбца:
  - `is_processed` — «это сообщение уже разобрано или ещё ждёт пачку»;
  - `quoted_message_id` — на какое сообщение был ответ-цитата (нужно, чтобы
    восстановить связь цитаты при разборе пачки).
- **`batch_extractor.py`** — формирует тот самый «большой запрос»: берёт пачку
  сообщений с пометками тредов и цитат и просит LLM вернуть список действий.
- **`batch_processor.py`** — оркестратор («повар»): собирает пачку из базы,
  считает эмбеддинги, зовёт LLM, применяет результат, помечает сообщения
  разобранными. Плюс будильник и фоновая ветка для явных привязок.
- **Маршрутизация** в обработчике входящих сообщений: решает, что отдать сразу,
  а что отложить в пачку.

## 4. Dev-скрипты: что создали и зачем

Это вспомогательные скрипты для ручной проверки — чтобы гонять batch вживую,
не дожидаясь реального чата.

### `scripts/seed.py` (был раньше)
Засевает в базу 8 готовых тестовых сообщений про вакансии (питонист, тимлид,
DevOps и т.д.), включая одно «мусорное» («Привет, как дела») для проверки, что
бот его отсеет. Использовали как стартовые данные для базового прогона.

### `scripts/run_batch.py`
Главный «запускатель». Один раз вызывает разбор созревших пачек и печатает:
сколько сообщений было необработанных до и после, сколько появилось вакансий, и
список вакансий. По сути — «нажать кнопку обработки руками» и сразу увидеть итог.

### `scripts/show_vacancies.py`
Показывает все вакансии вместе с их историей изменений (ревизиями:
создание / обновление / закрытие). Этим скриптом проверяли результат после
каждого прогона — например, что три сообщения про питониста дали **одну**
вакансию с тремя записями в истории, а не три отдельные вакансии.

### `scripts/seed_threads.py`
Засевает специальные сценарии для проверки привязки:
- сообщения в **одном треде** («Ищем Scala-разработчика» + «теперь удалёнка»);
- сообщение-**цитата** без общего треда («Открыли Rust» + ответ «поднимаем до 360k»).
Follow-up'ы специально **без названия вакансии** — чтобы проверить, что связывает
именно структура (тред/цитата), а не смысл текста.

### `scripts/test_inline.py`
Проверяет фоновую ветку (конвейер 2): берёт **уже существующую** вакансию и
кидает в её тред новое сообщение. Убеждаемся, что оно обрабатывается **сразу**
(а не ложится ждать пачку).

### `scripts/test_edit.py`
Проверяет правку и удаление сообщений, которые **ещё ждут пачку**:
- правка → обновляется только текст, разбор остаётся за пачкой;
- удаление → сообщение помечается удалённым и в пачку не попадает.

### `scripts/test_edit_processed.py`
Проверяет правку и удаление **уже разобранных** сообщений (которые уже стали
вакансиями):
- правка → вакансия пересчитывается (например, зарплата меняется);
- удаление → если сообщение было единственным источником вакансии, удаляется и
  сама вакансия.

### `scripts/tests_triggers.py`
Проверяет два условия запуска пачки:
- **по количеству** — накопилось достаточно сообщений;
- **по времени** — сообщение «перевисело» таймаут, даже если их мало.

## 2. Теория тестирования: что разобрали

### Виды тестов (пирамида)

```
           /\
          /E2E\        ← мало, дорого, медленно
         /------\
        /  Integ  \    ← средний слой: API, БД
       /------------\
      /    Unit       \ ← много, дёшево, быстро
     /__________________\
```

- **Unit** — одна функция / класс, без внешних зависимостей. Детерминированные, изолированные.
- **Integration** — несколько модулей вместе: реальная БД или API.
- **E2E** — весь путь от входа до выхода (как Playwright для UI или ngrok-прогон для чат-бота).

### Паттерн AAA (Arrange / Act / Assert)

Структура каждого теста: сначала готовим данные, потом вызываем, потом проверяем результат. Делает тест читаемым: сразу видно, что тестируем и что ожидаем.

### `pytest.mark.parametrize`

Позволяет прогнать **одно тело теста** по списку входных данных — вместо 12 одинаковых функций пишем одну:

```python
@pytest.mark.parametrize("text", HIRING_MESSAGES)
def test_detects_hiring_announcements(text):
    assert is_new_posting(text) is True
```

pytest создаёт 12 отдельных тест-кейсов, каждый со своим именем. При падении сразу видно, на каком конкретном значении сломалось.

## 3. Рефактор для тестируемости: `posting_heuristic.py`

Перед написанием тестов наткнулись на проблему: функция `_is_new_posting` (regex-детектор найма) жила в `entity_resolution.py`, который на уровне импорта тянет openai + sqlalchemy и создаёт AsyncOpenAI-клиент из `settings`. Значит, тест даже одной regex-строки требовал `.env` и тяжёлых зависимостей.

**Решение:** вынести чистую логику в отдельный модуль.

- **Создали** `app/services/posting_heuristic.py` — только `import re`, функция `is_new_posting(text: str) -> bool`.
- **Изменили** `entity_resolution.py` — убрали дублирующий код, добавили `from app.services.posting_heuristic import is_new_posting`.

Результат: время теста хэвристики упало с ~2.2с до ~0.2с. Это и есть «настоящий изолированный юнит».

**Принцип:** мелкие чистые хелперы, которые хочется тестировать, выносим в модули без тяжёлых импортов. Но не дробим ради каждой строки — `_coerce_int` в `extractor.py` остался на месте, он логически там и нужен.

## 4. `conftest.py` — корневой файл фикстур

```python
os.environ.setdefault("DATABASE_URL", "postgresql+asyncpg://test:test@localhost/test")
os.environ.setdefault("OPENAI_API_KEY", "test-key")

@pytest.fixture
def anyio_backend() -> str:
    return "asyncio"
```

Зачем:
- `app.config.Settings()` при импорте требует `DATABASE_URL` и `OPENAI_API_KEY`. Без них pytest валится ещё до первого теста.
- `setdefault` — не перезаписывает реальные значения из `.env` локально, но даёт заглушки на CI.
- `anyio_backend` фикстура — нужна для плагина `anyio`; без неё async-тесты не запускаются.

## 6. Ключевые техники: вопросы и ответы

### Что такое `AsyncMock` и `mark.anyio`?

**`AsyncMock`** — подмена для функций, которые возвращают корутину. Обычный `Mock` вернёт `Mock`-объект; когда код делает `await chat(...)`, это упадёт. `AsyncMock` возвращает корутину, и `await` работает корректно.

**`pytest.mark.anyio`** — маркер из плагина `anyio`. Без него pytest не знает, как запустить `async def test_...()` (это просто корутина, которую никто не ждёт). Маркер говорит: «запусти через asyncio event loop». `pytestmark = pytest.mark.anyio` в модуле помечает все тесты сразу.

---

### Почему патчим `"app.llm.prefilter.chat"`, а не `"app.llm.client.chat"`?

Правило: **патчить там, где имя используется, а не там, где оно определено**.

`prefilter.py` сделал `from app.llm.client import chat` — это скопировало ссылку. После этого в `prefilter` есть своё имя `chat`. Если подменить оригинал в `client`, `prefilter` продолжит смотреть на свою старую ссылку. Нужно подменять именно `app.llm.prefilter.chat`.

---

### Что делает `mock_chat.assert_awaited_once()`?

Проверяет, что mock был вызван с `await` **ровно один раз**. Это важно: если функция дёрнула LLM дважды (например, из-за бага в retry) — тест упадёт, хотя результат мог быть верным. Дополнительные проверки:

- `await_count` — сколько раз вызвали
- `assert_awaited_once_with(...)` — один раз И с конкретными аргументами
- `await_args.kwargs["messages"]` — аргументы последнего вызова

---

### Почему в `test_returns_false_when_llm_says_no` нет `assert_awaited_once()`?

Тест проверяет только **логику обработки ответа** («no» → `False`). Что вызов произошёл вообще — это уже проверено в `test_returns_true_when_llm_says_yes`. Не нужно дублировать одну проверку во всех тестах — каждый тест фокусируется на своём.

---

### Что такое `mock_chat.await_args.kwargs["messages"]`?

`await_args` — объект `call`, который запомнил аргументы последнего `await`-вызова. `.kwargs` — именованные аргументы. Если функция была вызвана как `await chat(model="gpt-4o", messages=[...])`, то `mock.await_args.kwargs` == `{"model": "gpt-4o", "messages": [...]}`. Так проверяем, что передали правильный промпт, не зная заранее полный текст промпта — только его идентификатор.

---

### Как работает тест `test_parses_valid_json_response`?

```python
raw = '{"action": "create", "fields": {"salary_min": "300к"}, "confidence": 0.9}'
monkeypatch.setattr("app.llm.extractor.chat", AsyncMock(return_value=raw))

result = await extract_vacancy("ищем бэкендера", ...)

assert result.fields["salary_min"] == 300000  # "300к" → int
```

Шаги: подменяем LLM → `extract_vacancy` дёргает мок, получает строку → парсит JSON → создаёт `ExtractionResult` → валидатор модели запускает `_normalize_salary` → `"300к"` превращается в `300000`. Проверяем не то, что LLM вернул `"300к"`, а то, что **наш код** правильно обработал этот ответ.

---

### `side_effect` для retry-тестов

```python
mock_chat = AsyncMock(side_effect=["   ", valid_json])
```

`side_effect` как список — каждый вызов возвращает следующий элемент. Первый вызов → `"   "` (пустой) → код делает retry → второй вызов → `valid_json` → успех. Это единственный способ честно проверить retry-логику без реальной сети.

## 2. Изменения по файлам

### `alembic/versions/0004_batch_v2.py` — новая миграция (этап 0)

`chat_messages` получает четыре поля:

- `text_hash` — sha256 текста, «версия содержимого»; бэкфилл от текущего текста;
- `process_status` (`pending` | `processed` | `failed`) — замена голому
  `is_processed` с терминальным состоянием; бэкфилл из `is_processed`,
  который остаётся на переходный период и обновляется синхронно;
- `flush_attempts` — счётчик неудачных флашей (драйвер бисекции и dead-letter);
- `claimed_at` — задел под мультиворкер (пока всегда NULL).

Partial-индекс очереди пересоздан под новый статус
(`ix_chat_messages_unprocessed` → `ix_chat_messages_pending`). Перестройка
`vacancy_revisions` (поля LWW/replay) в миграцию НЕ включена — поедет вместе
с этапами 2–3.

### `app/services/hashing.py` — новый модуль

`sha256_hex()` — единственная точка вычисления `text_hash` в Python-коде,
формат совпадает с SQL-бэкфиллом миграции. Инвариант: hash обновляется всегда
вместе с text (persist + оба handle_edit).

### `app/services/ingest.py`

`persist_message` пишет `text_hash` при вставке.

### `app/services/edits.py`

- `handle_edit` (полный путь) обновляет `text_hash` вместе с текстом;
- `handle_edit_batch`: ветка «ещё не processed» теперь по `process_status`
  и тоже обновляет `text_hash` — именно это ловит правку во время флаша
  (условный mark увидит расхождение и оставит сообщение pending);
  правка `failed`-сообщения **воскрешает** его: `pending` + `flush_attempts=0`
  (возврат из dead-letter правкой текста человеком).

### `app/services/entity_resolution.py`

- `resolve_and_save` возвращает `uuid | None` затронутой вакансии — батчу
  нужно для карты `index → vacancy` (цепочки `link_to_index`);
- новый `verify_open_vacancy()` — защита от галлюцинаций LLM: ссылка
  применяется, только если id существует, не удалён и не закрыт;
- новый `apply_to_vacancy()` — применение экстракции к заранее известной
  вакансии (структурная связь из пачки), минуя эмбеддинг-резолв;
- `_create_vacancy` возвращает `vac.id` вместо `vac.title` (title никто не использовал).

Сама логика резолва (якорь/эмбеддинг/пороги) не тронута.

### `app/llm/batch_extractor.py` — новый контракт с LLM

- **Полное покрытие (B9):** «РОВНО ОДИН объект на КАЖДЫЙ индекс, action=none —
  явно; пропуск индекса — ошибка». «Модель забыла» (индекс отсутствует →
  повторный флаш) и «модель решила, что не про вакансии» (явный none →
  честный processed) теперь различимы.
- **`BatchItem` расширен:** `link_to_index` («та же сущность, что у сообщения N
  пачки») и `link_to_vacancy_ref` (метка `vN`). В промпте — приоритет привязки:
  цитата на [N] > цитата на [hN] > общий тред > смысловая связь > упоминание vN >
  ничего; привязка по совпадению зарплаты запрещена явно.
- **Метки vN вместо UUID:** вакансии в промпте нумеруются `[v1]`, `[v2]`… —
  короткую метку LLM не переврёт; маппинг в id на нашей стороне.
- **Секция истории `[hN]`** — read-only, с привязками «→ вакансия [vN] «title»».
- **`_validate_coverage`:** отброс индексов вне диапазона и дублей
  (первый вердикт побеждает).
- **Самопочинка парсинга:** при битом JSON ретрай дописывает в диалог битый
  ответ модели + текст ошибки — модель чинит себя со второй попытки,
  а не повторяет ошибку вслепую.

### `app/services/batch_processor.py` — пересобран целиком

**Выборка пачки (B6):** после базового `LIMIT batch_size` добираются хвосты
попавших тредов; `_cap_by_tokens` режет по токен-бюджету (`len(text)//3`)
только по границе треда; первая группа берётся всегда (иначе гигантский тред
заклинил бы очередь); остаток остаётся pending следующему тику.

**Флаш (B1/B2, B9, B11):**
- `flush_batch` берёт lock конкретного space; занят → пропуск тика (B12);
- снапшот `id → text_hash` снимается ДО любой работы; сквозной `batch_id`
  во всех логах флаша (этап 9);
- пропущенные LLM индексы → `flush_attempts += 1`, остаются pending;
- `_apply_items`: items в порядке `message_index`; перед каждым — перепроверка
  `text_hash`/`is_deleted` (правка/удаление за время LLM-вызова → пропуск);
  исключение на item не прерывает цикл;
- `_apply_one`: приоритет `link_to_index` (карта index→vacancy; цепочки
  [4]→[2]→[0] работают) → `link_to_vacancy_ref` (с верификацией) → старый
  `resolve_and_save` как fallback;
- `_mark_processed_conditional`: processed только успешно применённым,
  не изменившимся и не удалённым; остальные остаются pending.

**Устойчивость (B10):** общий сбой флаша → `flush_attempts += 1` всем;
сообщение с `attempts >= 3` в пачке → бисекция по границе тредов, половины
флашатся независимо (за log2(N) тиков яд изолируется); одиночное с
`attempts >= 5` → `process_status='failed'` (dead-letter), очередь
разблокирована.

**Триггер (B13):** `cnt >= batch_size` ИЛИ `тишина >= quiet_seconds (75)` ИЛИ
`oldest >= batch_timeout_seconds (300)`. Основной — quiet window: пачки
совпадают со всплесками разговора, родственные сообщения оказываются вместе.

**Онлайн-ветка (этап 8):** thread-reply с якорем, у которого в том же треде
ждёт пачки более старое сообщение, уходит в пачку вместе с ним — цельный разбор
треда одним LLM-взглядом вместо двух независимых. Пометка processed
онлайн-веткой тоже стала условной (по text_hash).

## 4. Сценарии «как это теперь работает»

**Правка во время флаша (B1).** Пачка ушла в LLM → пришла правка →
`handle_edit_batch` обновил `text` и `text_hash` → условный mark видит
расхождение хэша и НЕ помечает сообщение → следующий тик берёт его со свежим
текстом. Правка не глотается.

**Follow-up через границу пачек (B7).** «По нему подняли до 400» пришёл, когда
оригинал уже разобран предыдущей пачкой → в markup новой пачки оригинал виден
как `[h3] Иван → вакансия [v1] «Backend (Python)»: …` → LLM возвращает
`link_to_vacancy_ref: "v1"` → точный lookup вместо эмбеддинга с порогом 0.75.

**create + update в одной пачке (B8).** `[0]` создал вакансию, `[2]` пришёл с
`link_to_index: 0` → update применяется к вакансии из карты index→vacancy
напрямую, эмбеддинг-поиск не вызывается.

**Ядовитое сообщение (B10).** Пачка из 8 стабильно ломает LLM → attempts
дорастает до 3 → бисекция: 4+4, здоровая половина проходит → больная делится
дальше → одиночное ядовитое набирает 5 попыток → `failed` + лог
`batch_message_dead_lettered`. Очередь space разблокирована; правка текста
человеком возвращает сообщение в работу.

## 6. Что осознанно отложено (и почему)

**Этапы 2–3: LWW + replay (закрывают B3 полностью и B4).** Это перестройка
семантики `vacancy_revisions`: per-field ревизии, новый идемпотентный ключ с
`source_text_hash`, флаги `applied`/`is_superseded`, единый `replay_field`
вместо `_revert_message_deltas`. План сам требует для этого **бэктест на копии
БД** (реплей недельной истории, сравнение состояний вакансий до/после) —
катать такое одним заходом с остальным небезопасно. Текущая реализация
подготовлена к этому: все изменения вакансий уже идут через
`_update_vacancy`/`_create_vacancy`, у ревизий одна точка входа `_add_revision`.

**Мультиворкер (этап 7.3).** Поле `claimed_at` в схеме лежит, claim-механика
(`FOR UPDATE SKIP LOCKED`) не активирована — второго воркера нет, был бы

# Отчёт о работе: новые поля вакансии — location + additional_info

> Дата: 2026-06-11 · Ветка: `feature/batch-pipeline`

---

## 1. Что хотели

Добавить в карточку вакансии два атрибута:

- **`location`** — где предстоит работать («удалёнка», «Москва, офис», «гибрид, СПб»);
- **`additional_info`** — полезные детали, которые не ложатся в отдельные
  колонки (грейд, уровень языка, формат работы, бенефиты).

Оба — обычные `TEXT`-колонки с **семантикой замены**: новое сообщение про
вакансию перезаписывает поле (как `description`, `team` и остальные). Это
сознательный выбор — он вписывается в существующую модель ревизий и откатов
без её ломки. Вариант с «накоплением» (дописывать к старому) ломал бы чистый
откат правок в `edits.py`, поэтому отложен.

## 2. Обсудили и отвергли: слияние таблиц эмбеддингов и сообщений

По ходу всплыл вопрос — почему `chat_messages` и `chat_messages_embeddings`
лежат раздельно, нельзя ли вектор писать прямо в сообщение. Решили **оставить
раздельно**. Причина: `chat_messages` — горячая таблица, по строке постоянно
идут `UPDATE` статусов (`process_status`, `flush_attempts`), а вектор — ~6 КБ
и неизменен. В PostgreSQL любой `UPDATE` копирует всю строку (MVCC), так что
слияние тянуло бы 6 КБ вектора при каждом изменении статуса → раздувание
таблицы и деградация векторного индекса. Текущее разделение правильное.

## 3. Изменения по файлам

### Запись (поля доезжают до БД)

| Файл | Что |
|------|-----|
| `app/db/models.py` | `Vacancy.location` + `Vacancy.additional_info` (nullable TEXT) |

## 2. 🔴 Найден и починен критический баг

Локальный прогон сразу выявил баг, который **95 юнит-тестов не ловили** (он
проявляется только на живом PostgreSQL): `_mark_processed_conditional` падал на
ORM bulk-update (`executemany` + `bindparam` в WHERE → конфликт с
bulk-update-by-PK). Симптом: сообщения применялись к БД, но **не помечались
`processed`** → в batch-режиме это дубли вакансий и бесконечная переобработка.

Починка: один `UPDATE` с `WHERE (id, text_hash) IN (...)` через `tuple_` +
`synchronize_session=False`. После фикса — 77/77 сообщений помечаются.

**Вывод:** юниты с моками не видят поведение драйвера БД — нужен интеграционный
прогон. См. [[extract-model-needs-directive-prompts]].

# План доработок: найденные проблемы

> Дата обнаружения: 2026-06-11 · Источник: анализ `--diagnose` нагрузочного теста

---

## 🔴 Баг: `handle_edit_batch` теряет контекст при правке pending-сообщения

### Симптом

При прогоне `load_test.py` 8 сообщений с `ce=updated` («Поправка по X: вилку подняли до Y») получили `action="none"` и не создали ревизий. Все 8 вакансий для ролей 0–7 в итоге создались из других сообщений (`q-base-0..7`), а не из оригинальных объявлений.

Дополнительный каскадный эффект: 16 тред-сообщений для тех же ролей (`th-base-0..7` + `th-fu-0..7`) тоже получили `action="none"` — потому что их вакансии создались позже по таймлайну (из q-base), а батч уже обработал тред-сообщения к тому моменту.

### Корневая причина

`handle_edit_batch` для `pending`-сообщения просто **перезаписывает текст**:

```python
if row.process_status != "processed":
    row.text = msg.text      # оригинал "Открыли вакансию Python..." пропал
    row.text_hash = ...
    row.is_edited = True
    return                   # батч получит только новый текст
```

Батч флашит сообщение с текстом «Поправка по Python: вилку до 350k» без оригинала. LLM видит только поправку, но не знает **к чему** поправка — и говорит `action="none"`.

### Что нужно сделать

Вариантов несколько, нужно выбрать один:

**Вариант A (минимальный):** добавить колонку `original_text` в `chat_messages`. При первой правке `pending`-сообщения сохранять туда оригинал. Батч передаёт оба текста в промпт: «оригинал → правка». LLM понимает контекст.

**Вариант B (чище):** при правке `pending`-сообщения не перезаписывать его, а добавлять **новую запись** в `chat_messages` с тем же `thread_id`/`space_id` и специальным флагом `is_edit_of = <original_message_id>`. Батч при построении разметки подтягивает эту связь.

**Вариант C (workaround):** в `_build_markup` для сообщений с `is_edited=True` — явно добавлять пометку в промпт («это правка предыдущего сообщения»), чтобы LLM понимал что нет нужды искать оригинал.

### Приоритет

Средний — проявляется только при правке сообщения, которое ещё не успело обработаться. В реальном чате это возможно, но не частый сценарий. Тем не менее правка зарплаты в объявлении — важная операция, терять её нельзя.
